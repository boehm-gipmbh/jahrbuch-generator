== Übersicht

Dieses Runbook beschreibt den vollständigen Aufbau der asynchronen Video-Processing-Pipeline für den Jahrbuch-Generator. Videos werden nach dem Upload vom Backend per Kafka-Nachricht an einen dedizierten Worker delegiert, der FFmpeg-Verarbeitung auf einem separaten Root-Server (Netcup) durchführt.

=== Ziele

* FFmpeg-Verarbeitung vom Backend entkoppeln (kein Blockieren des Quarkus-Event-Loops)
* Worker läuft auf eigenem Server (Netcup) mit ausreichend CPU/RAM
* Kommunikation über WireGuard VPN (kein öffentliches Netz)
* Staging- und Prod-Umgebung getrennt

== Voraussetzungen

=== WireGuard-Tunnel aufbauen

Der WireGuard-Tunnel zwischen Hetzner und Netcup muss vor allem anderen eingerichtet sein.

==== Hetzner (`/etc/wireguard/wg0.conf`)

[source,ini]
----
[Interface]
PrivateKey = <HETZNER_PRIVATE_KEY>
Address = 10.0.0.1/24
ListenPort = 51820

[Peer]
PublicKey = <NETCUP_PUBLIC_KEY>
Endpoint = 185.163.117.234:51820
# WICHTIG: 10.0.1.0/24 hinzufügen damit Antworten an Docker-Container zurückgeroutet werden
AllowedIPs = 10.0.0.2/32
PersistentKeepalive = 25
----

IMPORTANT: `AllowedIPs` auf Netcup-Seite muss `10.0.1.0/24` enthalten (Docker-Subnet von Hetzner). Ohne das verwirft WireGuard auf Netcup alle Pakete mit Source-IP aus dem Container-Subnet.

==== Netcup (`/etc/wireguard/wg0.conf`)

[source,ini]
----
[Interface]
PrivateKey = <NETCUP_PRIVATE_KEY>
Address = 10.0.0.2/24
ListenPort = 51820

[Peer]
PublicKey = <HETZNER_PUBLIC_KEY>
Endpoint = 178.105.56.161:51820
# WICHTIG: 10.0.1.0/24 damit Antworten an Backend-Container geroutet werden
AllowedIPs = 10.0.0.1/32, 10.0.1.0/24
PersistentKeepalive = 25
----

WireGuard aktivieren:

[source,bash]
----
# Auf beiden Servern:
systemctl enable --now wg-quick@wg0

# Verbindung testen:
ping -c 3 10.0.0.2   # von Hetzner aus
ping -c 3 10.0.0.1   # von Netcup aus
----

==== WireGuard-Konfiguration live updaten (ohne Neustart)

Falls die `AllowedIPs` nachträglich ergänzt werden müssen:

[source,bash]
----
# Auf Netcup: Docker-Subnet zu AllowedIPs hinzufügen
wg set wg0 peer <HETZNER_PUBLIC_KEY> allowed-ips 10.0.0.1/32,10.0.1.0/24

# Route für Docker-Subnet auf Netcup hinzufügen
ip route add 10.0.1.0/24 dev wg0

# Persistieren in wg0.conf und systemd-Einheit neu laden
wg-quick strip wg0 > /etc/wireguard/wg0.conf  # VORSICHT: zerstört Kommentare
# Besser: manuell in wg0.conf AllowedIPs ergänzen
----

== Hetzner-Server: nftables-Regeln

=== Problem: Docker-INTERNAL Isolation

Docker setzt automatisch DROP-Regeln in `ip raw PREROUTING` um Container-IPs zu schützen. Da `docker0` das Subnetz `10.0.0.0/24` hat — identisch mit dem WireGuard-Subnetz — wird die WireGuard-IP `10.0.0.2` ebenfalls durch diese Regel geschützt:

[source]
----
ip daddr 10.0.0.2 iifname != "docker0" counter drop   # handle 7
----

Diese Regel droppt ALLE Pakete an `10.0.0.2` die nicht von `docker0` kommen — also auch den Backend-Container-Traffic über die Coolify-Bridge.

=== Fix: Exception-Regel einfügen

[source,bash]
----
# Prüfen welche Handle-Nummer die DROP-Regel hat:
nft -a list chain ip raw PREROUTING | grep '10.0.0.2'
# Ausgabe: ip daddr 10.0.0.2 iifname != "docker0" ... drop # handle 7

# Exception VOR dem DROP einfügen (position = Handle-Nummer des DROP):
nft insert rule ip raw PREROUTING position 7 \
  ip saddr 10.0.1.0/24 ip daddr 10.0.0.2 counter return

# Prüfen:
nft -a list chain ip raw PREROUTING | grep -A1 -B1 '10.0.0.2'
----

IMPORTANT: Docker erneuert diese PREROUTING-Regeln beim Neustart des Docker-Daemons (aber nicht beim Container-Neustart). Nach einem `systemctl restart docker` muss die Exception-Regel erneut eingefügt werden.

=== FORWARD-Regeln für WireGuard ↔ Coolify-Bridge

[source,bash]
----
# Coolify-Bridge-Interface ermitteln:
ip link show | grep 'br-'
# Beispiel: br-0df7bb5ff836

# FORWARD-Regeln setzen:
iptables -I FORWARD -i br-0df7bb5ff836 -o wg0 -j ACCEPT
iptables -I FORWARD -i wg0 -o br-0df7bb5ff836 -j ACCEPT

# MASQUERADE damit Container-IPs (10.0.1.x) über WireGuard NAT'd werden:
iptables -t nat -I POSTROUTING -s 10.0.1.0/24 -o wg0 -j MASQUERADE

# Regeln persistent speichern:
apt-get install -y iptables-persistent netfilter-persistent
netfilter-persistent save
----

NOTE: Die MASQUERADE-Regel für wg0 ist technisch redundant wenn WireGuard's AllowedIPs auf Netcup `10.0.1.0/24` enthält (dann wird keine Source-NAT benötigt). Sie schadet aber nicht.

=== Vollständige nftables-Prüfung nach Setup

[source,bash]
----
# FORWARD-Chain prüfen (unsere Regeln müssen VOR DOCKER-USER stehen):
nft list chain ip filter FORWARD

# PREROUTING-Exception prüfen:
nft list chain ip raw PREROUTING | grep '10.0.0.2'

# Konnektivitätstest vom Backend-Container:

----

== PostgreSQL: pg_hba.conf für Netcup-Zugriff

Der Worker verbindet sich über WireGuard von Netcup (10.0.0.2) zu PostgreSQL auf Hetzner. Durch Docker-NAT auf Hetzner kommt die Verbindung mit einer unbekannten Source-IP an.

=== Problem: SCRAM-SHA-256 schlägt fehl

Docker-proxy NAT-ed die Source-IP des Workers. `pg_hba.conf`-Regel matcht zu früh mit `scram-sha-256` → Authentifizierung schlägt fehl weil die Source-IP nicht mit dem Passwort-Hash übereinstimmt.

=== Fix: Trust-Regel für alle Host-Verbindungen

Im PostgreSQL-Container (Coolify):

[source,bash]
----
# pg_hba.conf des Staging-DB-Containers bearbeiten:
CONTAINER_ID=<staging-db-container-id>  # z.B. ym4jgfx36yb1ddihok0ttqm6
docker exec $CONTAINER_ID bash -c "
echo 'host all all all trust' >> /var/lib/postgresql/data/pg_hba.conf
"
# Reload (kein Neustart nötig):
docker exec $CONTAINER_ID psql -U postgres -c 'SELECT pg_reload_conf()'
# Neustart für pg_hba-Änderungen ist oft dennoch nötig:
docker restart $CONTAINER_ID
----

WARNING: `trust` ohne IP-Einschränkung ist unsicher für öffentlich erreichbare Datenbanken. Da die DB nur über WireGuard (10.0.0.0/24) erreichbar ist, ist dies akzeptabel. Ideal wäre eine Einschränkung auf `10.0.0.0/24`.

== Bekannte Probleme und Lösungen

=== Problem 1: docker0 / WireGuard Subnetz-Konflikt

**Symptom:** Backend-Container (10.0.1.x) kann 10.0.0.2:9093 (Redpanda) nicht erreichen. `Kafka Bootstrap broker disconnected`.

**Ursache:** Docker0 nutzt `10.0.0.0/24` — identisch mit WireGuard. Docker setzt DROP-Regel in `ip raw PREROUTING` für alle Pakete dst=10.0.0.2 die nicht von docker0 kommen.

**Diagnose:**

[source,bash]
----
# Paket-Tracing einschalten:
nft add table ip trace_table
nft add chain ip trace_table trace_chain '{ type filter hook prerouting priority -300; }'
nft add rule ip trace_table trace_chain ip saddr 10.0.1.0/24 meta nftrace set 1
nft monitor trace
# Im anderen Terminal: Verbindungstest triggern
# Dann trace_table wieder löschen:
nft delete table ip trace_table
----

**Lösung:** Exception-Regel + FORWARD-Regeln (siehe Abschnitt 4).

**Dauerlösung (TODO):** docker0 auf nicht-kollidierendes Subnetz (z.B. `172.17.0.0/16`) umstellen via `/etc/docker/daemon.json`:

[source,json]
----
{
  "bip": "172.17.0.1/24"
}
----

---

=== Problem 2: Redpanda advertised-addr = localhost

**Symptom:** Kafka-Client verbindet sich initial (Bootstrap), disconnected dann sofort wieder. `Bootstrap broker 10.0.0.2:9093 disconnected`.

**Ursache:** Redpanda advertised `localhost:9093` in der Metadata-Response. Der Kafka-Client versucht dann `localhost:9093` zu erreichen — nicht erreichbar von Hetzner aus.

**Lösung:** `--advertise-kafka-addr PLAINTEXT://10.0.0.2:9093` in den Redpanda-Start-Argumenten setzen.

---

=== Problem 3: PostgreSQL-Authentifizierung schlägt fehl von Netcup

**Symptom:** Worker startet, Fehlermeldung: `password authentication failed for user "postgres"`.

**Ursache:** Docker-proxy auf Hetzner NAT-et die Source-IP des Workers. Die pg_hba.conf-Regel für `scram-sha-256` matcht zuerst.

**Lösung:** `host all all all trust` in `pg_hba.conf` hinzufügen und DB-Container neu starten.

---

=== Problem 4: Redpanda Port-Konflikte (Staging vs. Prod)

**Symptom:** Staging-Redpanda startet nicht. Port already in use.

**Ursache:** Staging und Prod nutzen beide `network_mode: host`. Alle Default-Ports von Redpanda (9092, 33145, 8082, 9644) kollidieren.

**Lösung:** Alle Redpanda-Ports für Staging auf alternative Ports umstellen:

[cols="2,2,2", options="header"]
|===
|Dienst |Prod-Port |Staging-Port
|Kafka |9092 |9093
|RPC |33145 |33146
|PandaProxy |8082 |8083
|Schema Registry |8081 |8084
|Admin API |9644 |9645
|===

---

=== Problem 5: SSH_PRIVATE_KEY libcrypto-Fehler

**Symptom:** `Error loading key "(stdin)": error in libcrypto`

**Ursache:** SSH Private Key in GitLab ohne abschließendes Newline gespeichert.

**Lösung:** Key in GitLab CI/CD Settings löschen und mit korrektem Newline-Abschluss neu einfügen. Typ muss `File` (nicht `Variable`) sein.

---

=== Problem 6: `docker compose restart` übernimmt keine .env-Änderungen

**Symptom:** Worker nutzt alte DB-Credentials obwohl `.env` geändert wurde.

**Ursache:** `docker compose restart` startet Container neu aber liest `.env` nicht neu ein. `.env` wird nur bei Container-Neuanlage (Recreate) gelesen.

**Lösung:**

[source,bash]
----
# FALSCH:
docker compose restart

# RICHTIG (erzwingt Recreate und liest .env neu):
docker compose up -d
----
