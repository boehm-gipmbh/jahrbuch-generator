== Integrativ lokal testen

Vollständiger Stack lokal hochfahren: PostgreSQL in Docker, Migrationen, Seed-Daten, Backend, Frontend.

=== Schritt 1: PostgreSQL starten

==== Neu starten (frische DB — z. B. nach neuen Migrationen)

[source,bash]
----
docker stop postgres-dev && docker rm postgres-dev && docker run -d --name postgres-dev -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=postgres -p 5432:5432 postgres:17
----

==== Weitermachen (Container bereits vorhanden, aber gestoppt)

[source,bash]
----
docker start postgres-dev
----

=== Schritt 2: Migrationen ausführen

`migrate.sh` prüft anhand der `schema_migrations`-Tabelle, was bereits angewendet wurde — bereits eingespieltes wird mit `[skip]` übersprungen. Bei einer aktuellen DB ist dieser Schritt ein No-op.

[source,bash]
----
export FREE_DATABASE_URL="postgresql://postgres:postgres@localhost:5432/postgres" && export MIGRATIONS_DIR="$(pwd)/src/main/resources/db/migration" && bash migrate.sh
----

=== Schritt 3: Seed-Daten einspielen

Legt folgende User an. Idempotent — kann mehrfach ausgeführt werden.

[cols="1,2,1,1,1"]
|===
|Name |E-Mail |Rolle |managedGroup |Passwort

|`admin` |admin@jamsintown.de |admin, user |- |Admin1234!
|`user` |user@jamsintown.de |user |- |User9999#
|`detlef` |drdboehm@jamsintown.de |user |- |Detlef9999#
|`ddet` |dboehm@arcor.de |group-admin, user |Hochzeitszeitung |Ddet9999#
|===

Erstellt auch 3 Test-Gruppen: Hochzeitszeitung, ABI 1985, ABI 1986. +
ddet ist Mitglied aller 3 Gruppen, verwaltet aber nur Hochzeitszeitung.

IMPORTANT: Erst Schritt 2 (Migrationen) ausführen — `import-dev.sql` benötigt die Spalte `managed_group_id` aus Migration V25.

[source,bash]
----
PGPASSWORD=postgres psql -h localhost -p 5432 -U postgres -d postgres -f src/main/resources/import-dev.sql
----

=== Schritt 4: Backend starten

[source,bash]
----
export DEV_DB_USERNAME=postgres && export DEV_DB_PASSWORD=postgres && ./mvnw compile quarkus:dev -Dquarkus.profile=local
----

Das Backend läuft auf http://localhost:8080.


NOTE: Wenn die lokale DB auf einem anderen Port läuft (z. B. 5434 nach einem Produktions-Spiegel), DB-URLs per `-D`-Flag überschreiben:

[source,bash]
----
export DEV_DB_USERNAME=postgres && export DEV_DB_PASSWORD=postgres && ./mvnw compile quarkus:dev -Dquarkus.profile=local -Dquarkus.datasource.reactive.url=postgresql://localhost:5434/postgres?ssl=false -Dquarkus.datasource.jdbc.url=jdbc:postgresql://localhost:5434/postgres
----

NOTE: Wenn Port 8080 belegt ist (z. B. durch GitLab Puma), Quarkus-Port überschreiben. Kompletter Override mit abweichendem HTTP-Port und DB-Port:

[source,bash]
----
export DEV_DB_USERNAME=postgres && export DEV_DB_PASSWORD=postgres && ./mvnw compile quarkus:dev -Dquarkus.profile=local -Dquarkus.http.port=8090 -Dquarkus.datasource.reactive.url=postgresql://localhost:5434/postgres?ssl=false -Dquarkus.datasource.jdbc.url=jdbc:postgresql://localhost:5434/postgres
----

=== Schritt 5: Frontend starten (separates Terminal)

[source,bash]
----
cd src/main/frontend && npm start
----

Das Frontend läuft auf http://localhost:3000 und proxied API-Calls auf :8080.

NOTE: Wenn das Backend auf einem anderen Port läuft (z. B. 8090), muss das Frontend das wissen.
`REACT_APP_API_URL` ist in `.env.development` als relativer Pfad definiert — der CRA-Dev-Server leitet ihn per `proxy` (`package.json`) weiter, das fest auf `:8080` zeigt.
Lösung: `.env.local` anlegen (von Git ignoriert) und einen absoluten URL setzen:

[source,bash]
----
echo "REACT_APP_API_URL=http://localhost:8090/api/v1" > src/main/frontend/.env.local
----

Danach `npm start` neu starten. Die Datei löschen, um zum Standard zurückzukehren.

docker stop postgres-dev && docker rm postgres-dev && docker run -d --name postgres-dev -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=postgres -p 5432:5432 postgres:17 && sleep 5 && export FREE_DATABASE_URL="postgresql://postgres:postgres@localhost:5432/postgres" && export MIGRATIONS_DIR="$(pwd)/src/main/resources/db/migration" && bash migrate.sh
----

== Produktions-DB lokal spiegeln / dumpen

Vor Arbeiten an der Datenbank empfiehlt es sich, die Produktion lokal zu spiegeln oder einen Dump zu erstellen.
Credentials liegen in `.env` (gitignored):

[source]
----
DEV_DB_USERNAME=postgres
DEV_DB_PASSWORD=<passwort aus Passwortmanager>
----

IMPORTANT: Die Produktions-DB läuft auf PostgreSQL 17. Das lokale `pg_dump` ist ggf. inkompatibel.
Daher wird `pg_dump` aus einem PostgreSQL-17-Docker-Container ausgeführt (`--network=host` damit der Container den Fly.io-Proxy auf localhost:5433 erreicht).

=== Option A: Nur Dump erstellen

[source,bash]
----
fly proxy 5433:5432 -a jahrbuch-generator-pg
----

In separatem Terminal offen lassen, dann:

[source,bash]
----
export $(grep -v '^#' .env | grep -v '^$' | xargs) && docker run --rm --network=host -e PGPASSWORD=$DEV_DB_PASSWORD postgres:17 pg_dump -h localhost -p 5433 -U postgres -d postgres > prod_dump_$(date +%Y%m%d).sql
----

NOTE: pg_dump gibt ggf. eine Warnung über zirkuläre Foreign Keys (Tabelle "nodes") — bei einem Full Dump unkritisch.

NOTE: `export $(cat .env | xargs)` schlägt fehl wenn die `.env` Kommentare enthält. Stattdessen `grep -v '^#' .env | grep -v '^$'` verwenden (filtert Kommentare und Leerzeilen).

=== Option B: Produktion in lokale Docker-DB spiegeln

[source,bash]
----
fly proxy 5433:5432 -a jahrbuch-generator-pg
----

In separatem Terminal offen lassen, dann:

[source,bash]
----
export $(grep -v '^#' .env | grep -v '^$' | xargs) && docker run --rm --network=host -e PGPASSWORD=$DEV_DB_PASSWORD postgres:17 pg_dump -h localhost -p 5433 -U postgres -d postgres | docker run --rm -i --network=host -e PGPASSWORD=postgres postgres:17 psql -h localhost -p 5432 -U postgres -d postgres
----

Danach Quarkus mit lokalem Profil starten (Schritt 4 oben).

=== Captures lokal verfügbar machen

Die Bilddateien sind nicht im DB-Dump enthalten — sie liegen auf Fly.io unter `/data/captures`.
Das Skript `fly-captures-download.sh` lädt sie per SFTP herunter nach `captures/` (gitignored).

Voraussetzung: Datei `jahrbuch-generator.token.ssh` im Projektroot (gitignored):

[source,bash]
----

----

Dann:

[source,bash]
----
./fly-captures-download.sh
----

NOTE: Die App schläft bei Inaktivität ein. Das Skript hält die App automatisch mit einem Ping-Loop wach.

== Frontend-Submodul: Pointer manuell aktualisieren

Das Frontend (`src/main/frontend`) ist ein Git-Submodul. Das Hauptrepo speichert nur einen Commit-Hash des Frontend-Repos — den "Pointer". Dieser wird normalerweise automatisch per CI/CD-Workflow gesetzt, sobald ein Frontend-PR auf `master` gemergt wird.

Wenn Frontend-Änderungen lokal (ohne CI/CD) gemacht und gepusht werden, muss der Pointer im Hauptrepo manuell nachgezogen werden.

=== Submodul-Pointer aktualisieren

[source,bash]
----
# 1. Im Frontend-Verzeichnis committen und pushen
cd src/main/frontend
git add .
git commit -m "feat: meine Änderung"
git push

# 2. Zurück ins Hauptrepo, Pointer per -a mitnehmen
cd ../../..
git commit -am "chore: Submodul-Pointer auf Frontend $(git -C src/main/frontend rev-parse --short HEAD)"

# 3. Push
git push
----

NOTE: Das `-a` in Schritt 2 staged automatisch alle bereits getrackten Änderungen — das Submodul zählt dazu. Neue (untracked) Dateien werden dabei nicht erfasst.

IMPORTANT: Submodul-Pointer-Commits dürfen **nur auf `main`** gemacht werden, nie auf Feature-Branches. Der Auto-CI/CD-Workflow setzt den Pointer nach jedem Frontend-Merge ebenfalls auf `main`. Zwei konkurrierende Pointer-Commits auf Feature-Branch und `main` erzeugen beim Rebase zwangsläufig Merge-Konflikte.

=== Wo steckt der Pointer?

[source,bash]
----
git ls-tree HEAD src/main/frontend
# → 160000 commit abc1234...  src/main/frontend
----

Der Modus `160000` zeigt: kein normaler Blob, sondern ein Submodul-Commit.

== Lokale PostgreSQL-Instanz reparieren

Die systemd-verwaltete PostgreSQL 16 auf Port 5432 wird in diesem Projekt nicht verwendet,
kann aber wie folgt repariert werden.

=== Passwort des postgres-Users zurücksetzen

[source,bash]
----
sudo -u postgres psql -c "\password postgres"
----

Falls dieser Befehl selbst nach einem Passwort fragt, zuerst die Authentifizierungsmethode temporär auf `peer` umstellen:

[source,bash]
----
sudo nano /etc/postgresql/16/main/pg_hba.conf
----

Zeile ändern: `local   all   postgres   md5` → `local   all   postgres   peer`, dann:

[source,bash]
----
sudo systemctl reload postgresql && sudo -u postgres psql -c "\password postgres"
----

Danach `pg_hba.conf` zurücksetzen und neu laden.

=== Instanz herunterfahren

[source,bash]
----
sudo systemctl stop postgresql && sudo systemctl disable postgresql
----

== Lokaler GitLab-Runner: Speicherplatz-Aufräumen

Der lokale CI-Runner (Shell-Executor) füllt mit der Zeit die Festplatte. Symptome im Build:
`No space left on device` während des Native-Builds, Quarkus-Tests oder beim Pullen von Docker-Images.

=== Diagnose

[source,bash]
----
df -h /
docker system df
sudo du -sh /home/gitlab-runner/builds/*/* 2>/dev/null | sort -h | tail -10
du -sh ~/.m2 /home/gitlab-runner/.m2 2>/dev/null
----

=== Standard-Aufräumen

[source,bash]
----
# Docker: alte Images, Container, Volumes entfernen (oft mehrere GB)
docker system prune -af --volumes

# Alte CI-Build-Workspaces (die letzten paar Builds reichen)
sudo find /home/gitlab-runner/builds -maxdepth 4 -type d -name target -exec rm -rf {} + 2>/dev/null

# node_modules in alten CI-Builds
sudo find /home/gitlab-runner/builds -maxdepth 5 -type d -name node_modules -exec rm -rf {} + 2>/dev/null
----

=== Häufige Speicherfresser

* `target/`-Verzeichnisse vom Native-Build: ~1–2 GB pro Lauf
* Docker-Images für `postgres:latest` und `quay.io/quarkus/ubi-quarkus-mandrel-builder-image:jdk-21`: ~3 GB zusammen, werden beim ersten Lauf gepullt und können danach gecached bleiben
* Maven-Cache `.m2/repository` im CI-Workspace: ~500 MB–1 GB pro Branch (über den `cache:`-Block in `.gitlab-ci.yml`)
* Playwright-Browser unter `~/.cache/ms-playwright/`: ~500 MB
