== Missing Features / UX Gaps

=== 17. Thumbnail-Generierung beim Upload ✅ ERLEDIGT
Thumbnails (400px, JPEG) werden automatisch erzeugt bei Upload, uploadcapture und nach Rotation.
`ExterneBilderResource` liefert Thumbnail via `?thumb=true` mit Fallback auf Original.
Frontend (`AuthImage.js`, `Bilder.js`) lädt in der Listenansicht Thumbnails.
`POST /generate-thumbs` generiert fehlende Thumbnails für bestehende Bilder nach.
`BildService.delete()` löscht Thumbnail mit. `SortableBildCard.js` (nur `feature-dnd`) bekommt `thumb` beim Merge.

=== 18. Virtuelles Scrollen statt Pagination
Klassische Pagination passt nicht zum Polling-Konzept (alle 10s) und würde DnD (Punkt 20) behindern, da alle Elemente im DOM verfügbar sein müssen.

Besserer Ansatz: **Virtuelles Scrollen** — alle Daten werden geladen, aber nur die sichtbaren Elemente werden gerendert. Die Render-Performance bleibt damit auch bei vielen Bildern gut.

Mögliche Bibliothek: `@tanstack/react-virtual` oder MUI `VirtualList`.

Betroffene Komponenten: `Bilder.js`, `Story.js`.

=== 19. Idee: Story-Fortschrittsanzeige
Jedes `Bild` und `Text` hat ein `complete`-Flag, aber die `Story`-Entity kennt keinen aggregierten Fortschritt.

Idee: Fortschrittsbalken oder Badge auf der Story-Karte in der Übersicht, z.B. "3 von 5 Bildern fertig".

Umsetzungsoptionen:
* Client-seitig: Bilder/Texte der Story filtern und `complete`-Flags zählen (keine Backend-Änderung nötig)
* Server-seitig: Neuer Endpunkt oder berechnetes Feld in der Story-Response

=== 25. Gemischte Bild+Text-Sortierung mit Layout-Modi

Bilder und Texte innerhalb einer Story sollen in einer gemeinsamen, per DnD frei sortierbaren Liste gemischt werden können. Zusätzlich soll die Story-Ansicht zwischen verschiedenen Layout-Modi umschaltbar sein (1-spaltig, Zeitungsstil 2-/3-spaltig, Grid).

==== Phase 1 – Backend: Gemeinsamer Reorder-Endpunkt

Neuer Endpunkt `PUT /api/stories/{storyId}/reorder` in `StoryResource`/`StoryService`.

Request-Body: geordnete Liste mit Typ-Tags:
[source,json]
----
[{"type": "bild", "id": 3}, {"type": "text", "id": 7}, {"type": "bild", "id": 5}]
----

`StoryService.reorder()` weist jedem referenzierten `Bild` bzw. `Text` `position = index` zu (gemeinsamer Namespace). Die bestehenden Einzel-Endpunkte (`/bilder/reorder/{storyId}`, `/texte/reorder/{storyId}`) bleiben für die Einzel-Ansichten erhalten.

Betroffene Klassen: `StoryResource.java`, `StoryService.java`

==== Phase 2 – Frontend: Einheitlicher DnD-Kontext

In `Story.js` werden Bilder und Texte zu einer gemeinsamen Liste zusammengeführt und nach `position` sortiert:

[source,js]
----
const items = [
  ...sortedBilder.map(b => ({ type: 'bild', id: `bild-${b.id}`, item: b })),
  ...sortedTexte.map(t => ({ type: 'text', id: `text-${t.id}`, item: t })),
].sort((a, b) => a.item.position - b.item.position);
----

Ein einzelner `DndContext` ersetzt die zwei getrennten. `handleDragEnd` ruft den neuen gemeinsamen Endpunkt auf (mit optimistischem Update auf beide Caches).

Neue Komponente `SortableStoryItem.js` — rendert je nach Typ entweder `SortableBildCard` oder eine Card-Variante des Textes. Beide benötigen dieselbe äußere Container-Form (Box/Paper statt TableRow) damit alle Layout-Modi funktionieren.

Neuer API-Endpunkt in `stories/api.js`: `reorderStory` mit optimistischem Update auf `getBilder`- und `getTexte`-Cache.

Betroffene Dateien: `Story.js`, `SortableBildCard.js`, `SortableTextRow.js`, `stories/api.js`, neu: `SortableStoryItem.js`

==== Phase 3 – Layout-Umschalter

`ToggleButtonGroup` oben in der Story-Ansicht, Präferenz per `storyId` in `localStorage` gespeichert (kein Backend nötig).

[cols="1,3,2"]
|===
|Modus |Darstellung |DnD-Strategie

|`1col` |Einzelspalte, gestapelt |`verticalListSortingStrategy`
|`2col` |CSS `columns: 2`, `break-inside: avoid` |`rectSortingStrategy`
|`3col` |CSS `columns: 3` |`rectSortingStrategy`
|`grid` |MUI Grid xs=12 sm=6 md=4 |`rectSortingStrategy`
|===

DnD operiert immer auf der flachen logischen Liste — die Spalten sind reines CSS-Display.

Neue Dateien: `StoryLayoutSwitcher.js`, `SortableStoryItem.js`

==== Offene Fragen (vor Umsetzung klären)

* *TextRow-Form:* Kompakte TableRow als eigenen Layout-Modus behalten, oder im gemischten Modus immer Cards verwenden?
* *Alter 2-Spalten-Split:* Als zusätzlichen Layout-Modus behalten (Texte links / Bilder rechts) oder vollständig ersetzen?
* *Position-Konflikt beim ersten Speichern:* Bestehende Bilder und Texte haben alle `position=0` — erst beim ersten Speichern nach dem Deployment wird die Reihenfolge korrekt gesetzt. Akzeptabel?

=== 26. Flyway-Migrationen einführen ✅ ERLEDIGT

DB-Migrationen sind versioniert und automatisiert. Da `quarkus.flyway.migrate-at-start=true` in Quarkus Native nicht zuverlässig feuert, werden Migrationen über den Fly.io `release_command` ausgeführt:

* `migrate.sh` — Shell-Script mit `schema_migrations`-Tracking-Tabelle, läuft vor jedem Deployment
* `fly.toml` — `[deploy] release_command = "/deployments/migrate.sh"`
* `src/main/resources/db/migration/V1__initial_schema.sql` — initiales Schema
* `src/main/resources/db/migration/V2__add_last_rotated.sql` — `last_rotated`-Spalte
* Flyway bleibt für lokale Entwicklung (JVM-Modus) aktiv via `migrate-at-start=true`

Neue Migrationen als `V3__...`, `V4__...` in `db/migration/` ablegen — werden automatisch beim nächsten Deployment angewendet.
